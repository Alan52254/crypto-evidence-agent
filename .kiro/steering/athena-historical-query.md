# Athena 歷史資料查詢策略

本指引定義 `athena_historical_query` 工具的觸發時機。
模型在 plan 階段必須依此判斷是否查詢歷史倉儲。

## 何時應該呼叫 athena_historical_query

1. **使用者問題明確涉及歷史比較**
   - 「跟去年同期比」「上次升息時 BTC 怎麼走」「過去半年表現」
   - 任何含有「歷史」「過去」「之前」「同期」「回顧」等詞彙的問題

2. **需要統計基準線來支撐當前判斷**
   - 當前波動率是否異常 → 查歷史波動率均值和標準差
   - 當前成交量是否放量 → 查歷史平均成交量
   - 當前價格位於歷史區間的什麼位置 → 查期間最高/最低

3. **宏觀環境切換判斷**
   - Fed 利率政策變化 → 查 FEDFUNDS 歷史趨勢
   - CPI 數據發布 → 查 CPIAUCSL 歷史走勢做對比
   - 美元指數異動 → 查 DTWEXBGS 歷史
   - M2 供應量變化 → 查 M2SL

4. **回測驗證**
   - 使用者要求驗證某策略的歷史績效
   - 使用者問「如果當時買入現在會怎樣」

5. **跨時間窗口分析**
   - 比較不同月份/季度的表現差異
   - 分析週期性模式（季節性效應）

## 何時不應該呼叫

- 使用者只問即時行情（「現在 BTC 多少錢」）→ 用 Binance/CoinGecko 即時來源
- 資料倉儲中沒有對應時段的資料（尚未 ingest 的時段）
- 已從即時來源取得足夠證據，且問題不涉及歷史對比
- 使用者問的是新聞事件本身（不是事件對價格的歷史影響）

## 查詢類型選擇

| 使用者意圖 | query_type | 附加參數 |
|-----------|-----------|---------|
| 價格統計/趨勢/波動 | ohlcv_summary | start_date, end_date, interval |
| 宏觀指標趨勢 | macro_trend | indicator, start_date, end_date |
| 複雜自訂分析 | custom_sql | sql (僅 SELECT) |

## 與即時來源的協作原則

- 歷史資料是**補充**，不是替代。先用即時來源建立當前狀況，再用歷史提供脈絡。
- 報告中引用歷史數據時，必須明確標註時間範圍，避免讀者誤認為當前數據。
- 如果歷史查詢回傳空結果，以現有即時證據繼續分析，不阻斷報告產出。
