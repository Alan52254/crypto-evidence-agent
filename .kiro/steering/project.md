# HoyaBit 分析 Agent — Kiro Steering

在這個 repo 工作時請遵守以下規則。它們是設計決策，不是風格偏好；
每一條後面都有對應的 ADR 或研究文件。

## 不可妥協的規則

1. **無證據的判斷進不了報告。** 推理層輸出結構化物件陣列，引用檢核對陣列過濾，
   Markdown 在過濾之後才渲染。**絕不先生成散文再依標點剪裁句子。**
2. **幣種閘門是白名單，不是黑名單。** 系統不判斷任何資產「是不是水幣」，
   只判斷它在不在 `Asset` 列舉內。不要新增迷因幣偵測邏輯。
3. **信心度是證據面之間的一致程度**（`docs/adr/0002`），不是模型的自我感覺。
   只由**有表態的面**計算 —— 中性面不投票。「證據不足」是與「低信心度」不同的第三態。
4. **轉載不構成獨立證據。** 同事件跨來源歸併後只計一個證據，但保留所有來源片段。
5. **資料源失效以空集合表達，不以例外表達。** 掛起、逾時、報錯一律等價。
   每個證據源都有硬性的單次 I/O 逾時上限。
6. **永不因逾時而失敗。** 預算耗盡時回傳「以現有證據組裝的報告」。
7. **工具切分只看有無外部 I/O。** 有 → MCP 工具；沒有 → Function 工具。
   這條線同時是測試邊界、故障邊界、部署邊界。

## 工具規格：一份，三個消費者

`ToolSpec`（`seams.py`）同時餵給三個地方，**不可以各自定義**：

1. Gemini 的 `functionDeclarations`（`models/gemini.py`）
2. MCP 的 `inputSchema`（`mcp_server.py`）
3. 我們自己的執行器（`run.py`）

新增資料源時只寫一份 `spec`，三邊自動同步。

## 版本鎖定

`mcp` **必須**寫死上界。2026-07-28 規格是 launch 以來最大的破壞性改版，
Python SDK v2 是為它重寫的。4 週內不得升 2.x。見 `docs/research/0001`。

## 測試慣例

- 所有流程測試打**接縫 2**（`analyse`），在接縫 1 塞假證據源、接縫 3 塞腳本假模型。
- **測試不碰網路、不呼叫真實模型。** 外部 HTTP 一律用 `httpx.MockTransport`。
- Function 工具（`tools.py`、`indicators.py`、`dedup.py`、`arguments.py`）
  **不需要任何 mock** —— 若你發現要 mock 才能測，那東西放錯層了。
- 測試名稱描述使用者可觀察的行為，不是函式名稱。

## Git 分支規則

- **不要直接 commit 到 `main`。** 所有改動一律在我的 feature branch 上做。
- 分支命名：`feature/<簡短描述>`，例如 `feature/coingecko-source`、`feature/time-window`。
- 完成後 push 到 remote 的我的分支。
- 不要 rebase 或 force push 隊友的 commit。
- 程式碼可以自由修改，不需要避開隊友的檔案。只要最終 push 到我的分支即可。

## 資訊不足時的處理原則

- **動手前必須確認資訊完整。** 如果我對需求、規格、格式、API 規範等有任何不確定，
  我必須**先停下來問你**，不能猜測或自行假設。
- 告訴你我缺什麼資訊、為什麼需要它、以及推薦你去問哪個 AI 或查哪份文件。
- 你回覆後我才動手。這條規則優先於「預設動手做」。
