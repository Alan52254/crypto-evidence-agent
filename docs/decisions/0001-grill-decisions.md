# ADR 0001 — 專案基礎決策紀錄

- **日期**：2026-07-23
- **來源**：`/grill-me` 十輪逼問（stateless grilling，greenfield 專案）
- **狀態**：已確認
- **專案**：HoyaBit AI 加密貨幣分析 Agent（黑客松命題 + 產品接縫）

## 背景

材料中混雜兩個不同的東西，必須先分開：

- **(A) HoyaBit 產品面** — 交易所本身：19 種幣定期定額（最低 70 元）、7 秒鎖價統一成交、
  台新銀行 24/365、ISO 27001、AI 金寶交易管家（浮動桌寵 + ChatBot 路由）。
- **(B) AI 命題** — ReAct Agent，15 分鐘內跑完，多源整合（籌碼面／技術面／基本面 + 社群情緒
  + 市場 API），只做 BTC/ETH/SOL/BNB/XRP，**禁止直接調用已有結論的 API**，
  要有完整的 point-to-point 推理 Log，AWS Kiro 加分（每位參賽者 2000 點）。

兩者成敗標準不同：(A) 要能上線、合規、成本可控；(B) 是給評審看的，重點在 Log 的說服力，
token 消耗明確不是評分重點。

## 決策

| # | 主題 | 決策 |
|---|---|---|
| 1 | 交付定位 | 競賽優先；**資料層、Agent 邊界、Log 格式**三處按生產規格留接縫，其餘走最短路徑 |
| 2 | 輸出契約 | 給方向（偏多／偏空／中性）+ 信心度，**每句判斷強制掛證據 ID**；無證據的句子在組裝階段被擋下 |
| 3 | 資料層 | 混合：背景 ingestion 進向量庫 + 即時 API 補齊。賽前必須先上線跑一段時間 |
| 4 | 自家資料 | **授權可用，限聚合層**（分幣種成交量、買賣盤比、定期定額淨流入、新增持倉帳戶數）；絕不碰單一帳戶 |
| 5 | 情緒源預算 | 只用免費源 + WebSearch；adapter 介面留給 X API，隨時可加購 |
| 6 | 模型 | **分層**：雲端旗艦跑 ReAct 推理與報告撰寫；小模型跑情緒打分／摘要／去重。兩層都藏在同一 provider 介面後 |
| 7 | 工具切分 | **以 I/O 邊界切**：有外部 I/O → MCP Tool；純計算 → Function Tool。此線同時是測試邊界與故障邊界 |
| 8 | 資源 | **4 週、2-3 人** |
| 9 | Log | 自建結構化 trace schema（JSONL）+ 輕量時間軸／樹狀前端。**trace 檔本身是交付物**，不是 debug 副產品 |
| 10 | 4 週範圍 | 單幣分析 pipeline + Trace 視覺化前端 |

## 理由摘要

- **#2**：命題範例二（「多的結論從哪裡來」）不是獨立功能，逐句掛證據 ID 後自動被滿足，零額外成本。
  同時這是產品化時唯一需要改動的地方（外層換措辭 + 加免責），內核不用改。
- **#6**：ReAct 迴圈有兩種工作 —— 推理層（決定下一步、整合矛盾證據）能力天花板決定成敗；
  勞務層（單篇貼文打分、去重、摘要）呼叫次數是推理層數十倍但每次都簡單。
  混用同一顆大模型會吃光 15 分鐘的壁鐘預算並撞 rate limit。
- **#7**：以 I/O 切的好處是判準只有一條、不會歧義；Function Tools 全部可無 mock 單元測試；
  外部源掛掉只影響 MCP 層，推理不會整個崩。
- **#9**：命題原文「要能看到不同 Agent 架構下，他的點對點之間為什麼結果這樣出來」、
  「不是只是問一個投顧」→ Log 是主要交付物。現成平台（LangSmith/Langfuse）呈現的是
  工程師視角的 span，不是「證據如何支撐結論」，評審看不出推理質地。

## 明確排除（4 週內不做，但留接縫）

- **跨幣種比較層（命題範例三）** — 邊際成本低（同 pipeline fan-out + 排序層，不重跑推理），
  但不排進 ticket。**設計上單幣分析必須是純函數、輸出結構化結論物件，天生可 fan-out**，
  第 3 週進度允許時加比較層應為 1-2 天，而非重構。
- **自家聚合指標真實串接** — 授權已給，但 4 週內只實作 adapter 介面與假資料，
  避免時程被內部資料開通流程綁架。
- **金寶桌寵前端** — 不在 4 週範圍。
