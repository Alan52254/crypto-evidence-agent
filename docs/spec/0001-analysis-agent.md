> 本規格全程使用 [CONTEXT.md](../../CONTEXT.md) 的術語。
> 「證據」「證據面」「判斷」「方向」「信心度」「推論軌跡」等詞都有精確定義，非泛稱。

## Problem Statement

加密貨幣市場全天候運作，能影響價格的資訊散落在市場數據、鏈上數據、新聞與社群之間，
而且彼此矛盾。想理解某個幣種當下的處境，人必須同時開十幾個分頁、自己判斷哪些資訊可信、
自己拼湊因果，而且做完之後**無法回答「我為什麼這樣認為」**。

市面上的 AI 工具給出的是一段沒有來源的文字：讀起來像結論，但無法查證、無法反駁、
也無法知道它漏看了什麼。使用者要的不是「一個看起來很懂的投顧」，
而是**一份可以逐句追回原始出處的分析**。

## Solution

一個 Agent，接受「分析某個受涵蓋幣種」的請求，在 15 分鐘內：

1. 從多個異質來源蒐集**原始**資料（不採用任何已含結論的來源），轉成帶識別碼的**證據**。
2. 由模型依據**證據缺口**動態決定下一步蒐集什麼 —— 這是真正的推理，不是固定管線。
3. 產出一份**分析報告**：一個方向、一個信心度、以及一組**每句都掛載證據識別碼**的判斷。
   無證據的判斷在組裝階段被丟棄。
4. 同時產出一份**推論軌跡**：每個決策點為何這樣選、輸入是什麼、產出哪些證據、
   如何改變了證據缺口。軌跡是交付物，不是除錯副產品。

使用者因此可以對報告中的任何一句話問「這是哪來的」，並得到原文片段、出處連結與擷取時間。

## User Stories

### 分析使用者

1. 作為使用者，我想指定一個受涵蓋幣種發起分析，以便取得該幣種當下的處境判讀。
2. 作為使用者，我想在報告開頭就看到方向與信心度，以便三秒內知道結論的份量。
3. 作為使用者，我想看到報告中每一句判斷後面都有證據標記，以便知道它不是憑空生成的。
4. 作為使用者，我想點擊任一證據標記看到原始片段、出處 URL 與擷取時間，以便自行查證。
5. 作為使用者，我想在四個證據面互相矛盾時被明確告知信心度低，以便不會誤信一個其實有分歧的結論。
6. 作為使用者，我想在證據不足時看到「證據不足」而非一個虛假的高信心度，以便知道系統沒查到東西。
7. 作為使用者，我想看到報告分別呈現技術面、籌碼面、基本面、情緒面各自的傾向，以便知道分歧出在哪一面。
8. 作為使用者，我想在請求非受涵蓋幣種時立刻被拒絕並得到清楚說明，以便不會浪費 15 分鐘等一份不會產出的報告。
9. 作為使用者，我想知道這份分析涵蓋的時間窗，以便判斷它的時效性。
10. 作為使用者，我想在分析進行中看到目前進度與已蒐集到的證據數，以便知道系統沒有卡住。
11. 作為使用者，我想在某個資料源失效時仍拿到一份報告（只是信心度較低），以便單一來源故障不會讓我一無所獲。
12. 作為使用者，我想看到報告明確標示它不是投資建議，以便理解它的性質。

### 評審 / 技術檢視者

13. 作為評審，我想看到完整的推論軌跡，以便判斷這是真的推理還是包裝過的固定流程。
14. 作為評審，我想在軌跡的每個節點看到「模型當時為何選擇這個動作」，以便理解點對點之間的因果。
15. 作為評審，我想看到模型在蒐集迴圈中**改變主意**的痕跡（發現缺口 → 補抓），以便確認迴圈是動態的。
16. 作為評審，我想看到軌跡節點與最終報告中判斷的連線，以便驗證結論確實由蒐集到的證據推出。
17. 作為評審，我想看到系統拒絕了哪些無證據的判斷，以便確認引用檢核真的在運作。
18. 作為評審，我想在時間軸上看到 15 分鐘預算的消耗分布，以便知道時間花在哪。
19. 作為評審，我想確認系統沒有調用任何「已含結論」的第三方 API，以便確認分析是自己做的。

### 開發者 / 維運者

20. 作為開發者，我想在不碰網路、不呼叫模型的情況下跑完整條分析流程的測試，以便 CI 能穩定執行。
21. 作為開發者，我想新增一個資料源時只實作一個介面，以便不必理解 Agent 的內部運作。
22. 作為開發者，我想替換推理層模型而不改動任何分析邏輯，以便能比較不同模型的表現。
23. 作為開發者，我想把資料源當作 MCP server 掛載到 Kiro 或 Claude Desktop，以便在對話中直接驗證資料正確性。
24. 作為開發者，我想在單元測試中完整測試所有計算邏輯而不需要任何 mock，以便測試快速且可信。
25. 作為維運者，我想在分析回合超過時間預算時得到一份「已知證據下的最佳報告」而非逾時錯誤，以便系統永遠有輸出。
26. 作為維運者，我想查詢過去任一分析回合的完整軌跡，以便事後檢討判斷品質。

## Implementation Decisions

### 分層與接縫

系統只有**三個接縫**，刻意壓到最少：

1. **證據源 (Evidence Source)** — `fetch(asset, window) → Evidence[]`。
   所有外部 I/O 藏在此後。真實適配器：Binance 公開 REST、新聞 RSS、CoinGecko Demo、
   本所聚合指標（僅介面＋假資料）；測試適配器：固定證據集。
2. **分析回合 (Analysis Run)** — `analyse(request) → (Report, Trace)`。
   **最高的接縫，也是主要測試面**。整條流程從這一個介面測完。
   依賴以參數注入，不在內部建構。
3. **模型供應者 (Model Provider)** — 兩個方法：`reason(...)`（推理層）、`label(...)`（勞務層）。
   測試時換成腳本化假模型。

測試策略：所有流程測試打接縫 2，接縫 1 塞假證據源、接縫 3 塞假模型
→ **完整 pipeline 不碰網路、不燒 token**。

### 幣種閘門

在分析回合開始**之前**執行的白名單比對，不是黑名單偵測。
系統不判斷任何資產「是不是水幣」—— 只判斷它在不在受涵蓋幣種集合內。
拒絕時回傳明確理由，不進入蒐集迴圈，不消耗任何預算。

### 固定骨架 + 迴圈內動態

分析回合的外層是固定的狀態圖（規劃 → 蒐集 → 缺口檢查 → 組裝），保證一定收斂；
**蒐集迴圈內部是真正的 ReAct** —— 呼叫哪些工具、要不要再挖一輪，
全由模型依據當前**證據缺口**決定。這同時滿足「必須是真推理」與「不能跑不完」。

蒐集迴圈的終止條件（任一成立即停）：四個證據面皆已達最低證據數；
模型判定無缺口；壁鐘預算耗盡；迴圈次數上限。

### 時間預算

15 分鐘是**上限不是目標**。預算由分析回合持有並在每個軌跡節點扣減。
預算耗盡時走「以現有證據組裝」路徑，**永不回傳逾時錯誤**——
一份低信心度的報告優於沒有報告。

### 證據模型

- 證據不可變，有穩定識別碼，永遠指向一則**來源片段**（原文 + 出處 URL + 擷取時間 + 位置）。
- **證據面與資料源正交**：同一資料源可產出多個面的證據（RSS 同時給基本面事實與情緒面片段）。
  因此不得設計成「一個面一個工具」。
- **情緒分數屬於單一片段**，落在 −1 到 +1。幣種層級的是**情緒彙總**，
  且必須能列舉出組成它的每一則片段。不得直接儲存幣種層級的分數。

### 信心度

依 [ADR 0002](../adr/0002-confidence-is-cross-facet-agreement.md)：
信心度是**證據面之間的一致程度**，由證據直接計算，本身可溯源。
每個證據面必須能獨立產出方向傾向。
**「證據不足」是與「低信心度」不同的第三態**，必須能分別表達。

### 報告組裝與引用檢核

**判斷必須以結構化物件生成，絕不可先生成 Markdown 散文再事後剪裁句子。**
推理層的輸出是判斷物件的陣列（每個物件含判斷文字、證據識別碼、所屬證據面），
以 structured output 強制約束。引用檢核是對這個陣列做過濾；
過濾後才由格式化器渲染成 Markdown。

若反過來做（先生成散文、再依標點切句丟棄），剩下的段落會出現主語遺失、
連接詞斷裂、語法崩潰 —— 既毀了可讀性，也讓「無證據不進報告」變成不可靠的字串處理。

組裝階段對每個判斷檢查是否掛載了至少一個有效的證據識別碼。
**未通過者直接丟棄，不進報告，但進軌跡**（讓評審看到檢核確實在運作）。

### 儲存

**PostgreSQL 16+ 搭配 pgvector**，向量與關聯式一套解決。
理由：證據溯源本質是 join（判斷 → 證據識別碼 → 來源片段 → 出處），
這是 SQL 擅長而純向量庫不擅長的；且資料量遠低於 pgvector 的實用上限。
避免「兩個儲存體資料不一致」這個 4 週內最不划算的問題。

### 工具切分

判準唯一：**有無跨行程 I/O**。
- **MCP 工具** — 各證據源存取、向量檢索。額外好處：可掛載到 Kiro / Claude Desktop 現場驗證。
- **Function 工具** — 技術指標計算、情緒彙總、證據去重、信心度計算、報告組裝與引用檢核。
  全部確定性、無 I/O、可無 mock 測試。

### 版本鎖定

`langgraph==1.2.9`、`langchain==1.3.14`、`llama-index-core==0.14.23`、`mcp==1.28.1`，
Python 3.11–3.12。**`mcp` 必須寫死上界** —— 2026-07-28 規格為破壞性改版，4 週內不得升級。

### 模型分層

- 推理層：Gemini 3.1 Pro 或 Claude Sonnet 5，藏在模型供應者介面後可切換。
- 勞務層：Gemini 2.5 Flash-Lite 起步（情緒打分、摘要、去重）。
- 兩層都可替換成假模型供測試。

### 資料源優先序與降級

Binance 公開 REST（無金鑰）→ 新聞 RSS（無金鑰）→ CoinGecko Demo（10k calls/月，
僅作補充欄位，**不得作為輪詢主力**）→ 本所聚合指標（介面 + 假資料）。
**任一證據源失效時，分析回合繼續進行**，該面的證據缺口反映在信心度上。

**證據源介面強制單次 I/O 逾時上限（10-15 秒）。掛起與失敗同義，都以空集合表達。**
沒有這道防護，一個網路波動造成的 hang 就能把 15 分鐘預算耗在無意義的等待上。
逾時後 ReAct 迴圈立即觀察到「該來源暫時不可用」並改變策略 ——
預算必須全部花在推理，而非等待。

### 證據獨立性

依 [ADR 0002](../adr/0002-confidence-is-cross-facet-agreement.md)，
證據在寫入前依同事件歸併：保留所有來源片段（溯源不損失），但**只計為一個證據**。
信心度的輸入是歸併後的證據。此規則適用於所有資料源，不是新聞源的特例。

## Testing Decisions

**什麼是好測試**：只測外部行為，不測實作細節。測試打接縫，不打接縫內部。
測試的名字描述使用者可觀察的行為，而非函式名稱。

- **分析回合（接縫 2）—— 主要測試面。** 塞假證據源與假模型，驗證：
  報告方向與信心度符合預期、無證據判斷被丟棄、預算耗盡時仍產出報告、
  資料源失效時流程繼續、證據不足時回傳第三態而非高信心度。
- **Function 工具 —— 無 mock 單元測試。** 技術指標計算、情緒彙總、去重、
  信心度計算、引用檢核。這些是確定性純函數，測試應該又快又多。
- **幣種閘門** — 受涵蓋幣種通過、其餘一律拒絕且不消耗預算。
  測試以集合為準，不列舉特定的被拒幣種。
- **證據源適配器（接縫 1）** — 各自針對「回傳的證據是否帶完整來源片段」測試。
  打真實 API 的契約測試單獨標記，不進 CI 主流程。
- **推論軌跡** — 驗證軌跡完整記錄每個決策點、且軌跡中的證據識別碼與報告中掛載的一致。

**先行技術**：無（greenfield）。第一張票即建立測試慣例，後續票沿用。

## Out of Scope

- **跨幣種比較層（命題範例三）** — 不排進 4 週，但單幣分析必須是**純函數、
  輸出結構化結論物件、天生可 fan-out**，使得後續加入比較層是 1-2 天而非重構。
- **金寶桌寵前端與 ChatBot 路由** — 完全在範圍外。
- **任何交易執行能力** — Agent 不得具備下單、兌換或任何動用資金的工具。只輸出分析。
- **本所聚合指標的真實串接** — 僅實作介面與假資料，避免時程被內部資料開通流程綁架。
- **Kubernetes、Prometheus、Grafana** — 可觀測性只做自建推論軌跡。
- **地端模型微調** — 見研究 0001 第 4.4 節的評估基準；微調無法改善最關鍵的多輪 tool calling 成功率。
- **Reddit 作為關鍵路徑** — OAuth 人工核准需 2-4 週。放在證據源介面後當可選來源。

## Further Notes

- **Reddit 申請是時程敏感項，須立即送出**（研究 0001 第 7 節）。
- **AWS Kiro 是開發用的 agentic IDE，不是 runtime 模型。** 2000 credits 是開發額度。
  競賽加分應透過展示 Kiro 的 spec 與 hooks 使用，而非宣稱系統主腦是 Kiro。
- 命題要求「不能直接調用已經有結論的 API」—— 本設計的所有證據源回傳的都是原始數值或原文，
  所有結論由 Function 工具計算或由推理層從證據推出。此約束應在驗收時逐一資料源複查。
